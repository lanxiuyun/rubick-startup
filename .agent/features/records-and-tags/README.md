# 记录与标签

列表里的每一项就是一条**字符串**（路径或命令）。给字符串打标签，它就永久保留。这是这个工具的核心资产模型 —— Win+R 的历史是一次性的，这里是积累性的。

## 涉及文件

- `src/StartupApp.tsx` — React 状态、虚拟列表、Ant Design 标签/菜单/编辑器与消息
- `src/model.mjs` — `visible()` 模糊过滤、`groupCounts()` 标签数量、`prune()` 保留规则
- `src/runtime.ts` — 原存储键、数据加载与保存
- `src/style.css` — 固定行高与 A「轻盈白底」局部布局
- `public/index.html` — 构建产物，不直接编辑

## 数据模型

一条记录存在 Rubick 的 PouchDB 里，整份数组放在**一个文档**里：

```js
{
  _id: 'rubick-startup/history-v2',   // PouchDB doc id（Rubick 会加 RUBICK_DB_DEFAULT/ 前缀）
  groups: ['IP查询','常用'],          // 独立标签名称列表，0 条也保留
  records: [
    { id:'run-<时间戳>-<随机>', command:'ipconfig /all', time:1791723508184,
      kind:'command'|'path',                 // 由 guessKind() 判断，只影响图标
      groups:['IP查询','常用'] }             // 多标签；空数组 = 临时历史
  ]
}
```

落盘在 `%APPDATA%\rubick\default`（LevelDB）。**磁盘上没有 `rubick.db` 这个文件** —— 那是 Rubick 注入页面的进程内 API。

## 两条保留规则

`prune()` 的实现：

- **有 `groups` 的记录永不清理**
- 没有标签的算临时历史，最多 `LIMIT = 500` 条，超出按最久未使用淘汰

也就是说上限只约束普通记录；被主动标记过的只增不减。

`error` 是红色的启动状态标签：已有记录再次启动失败时自动添加，并更新 `time` 为本次尝试时间；不创建首次失败记录。下一次成功启动时自动移除 `error`，保留用户添加的其它标签。该名称需视为保留标签，不用于表达手动分类。排序时间表示最近一次尝试，不仅是成功时间。

## 三个视图层约定

**1. 排序：纯按 `time` 倒序，不置顶。** 用户明确要求过"不要置顶，按最近使用排"。带标签的不会浮到顶部。

**2. 虚拟滚动靠固定行高。** `ROW_H = 56` 是常量，`.row` 用 `position:absolute; top:i*ROW_H`，`.spacer` 撑出 `total*ROW_H` 的真实高度。因此：

- **标签超过 2 个折成 `+N`** —— 这是为了保证行高恒定，不是为了省地方。标签数一多行高就变，滚动条会跳。
- 任何让行高变化的改动（换行、多行标签、可变高度）都会破坏虚拟滚动，必须同时改 `ROW_H` 与布局。

列表滚动条在 `.list` 上使用窄浅灰蓝滑块和透明轨道；保持原生滚动，不改变列表宽度、固定行高或虚拟滚动计算。

当前采用用户选定的 A「轻盈白底」：28px 图标槽、18px 无底框字形、56px 固定行高、13px 命令字体。内容区白底，与 Rubick 白色 header 衔接；记录选中用无边框淡青绿填充，顶部标签选中用淡青绿底与深青绿字，新建标签是带提示的加号按钮。切换标签只改配色，不改字重和尺寸，E2E 验证切换前后宽度一致。行内标签的名称和删除符分别占位，禁止悬停覆盖文字。不增加描述标题或分区信息。窄窗口减少行内间距，并限制标签区域占宽，优先保证命令阅读空间。

**3. 过滤范围是全部记录，不是"最近 N 条"。** `visible()` 在全部 500 条里模糊匹配命令与标签，所以老记录不会因为不在首屏就搜不到。

## 标签的几个设计决定

| 决定 | 原因 |
| --- | --- |
| 标签名称独立持久化到历史文档的 `groups` 字段 | 数量为 0、删除记录、重开插件都不会自动移除标签 |
| 旧记录标签与持久化名称合并 | 无需迁移操作，旧记录结构与存储键不变；下一次保存写入名称列表 |
| 删除标签 = 从名称列表删除并从所有记录移出 | 只有明确的删除操作才让标签消失 |
| 重命名标签 = 改所有记录上的引用 | 同上 |
| 没有 ☆ 收藏 | 标签就是收藏，一个概念不做两套 |

## 顶栏与执行反馈

顶栏只放标签筛选和新建标签，不显示运行环境检查或搜索输入回显。列表选择只改变行高亮，不改写其它界面内容；执行成功或失败通过短暂 toast 提示。

## 存储结构：不要改（有实测数据）

每次回车重写整个数组。有人会担心 500 条时卡顿 —— 实测**不卡**：

| 项目（N=500） | 中位 / p95 |
| --- | --- |
| `JSON.stringify(doc)` | 0.105 / 0.153 ms |
| PouchDB `get`+`put`（= `save()` 真实形状） | **1.294 / 1.884 ms** |
| Electron 真机 `sendSync`（76 KB 载荷） | **0.400 / 0.500 ms** |
| 端到端上界（IPC + 主进程 get+put） | **~1.7 ms，p95 < 4 ms** |

判据是 16 ms（掉帧）和 50 ms（可感知）。所以**没有**改成"每条一个文档"—— 那会让磁盘占用涨 4.4 倍（PouchDB 每条 doc 都有 `_rev`/rev-tree 开销）。

**触发改动的条件**：上限从 500 放到几千条（整份 put 约 2 µs/条线性增长），或要做多设备同步。
